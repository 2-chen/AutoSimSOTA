## 观察与修复

环境、训练器和原生评测入口已经存在；本窗口没有必要重新安装环境。Main完成一项官方权重reference计分后，后续训练被候选参数投影阻塞：稀疏idea只请求steps=80000，验证envelope却补入seed默认1000，执行前覆盖了基线20261013。冻结协议正确拒绝了这个实际漂移，但对外只给泛化的“candidate changes protocol”，Main因而多次修改无关参数／说明并调查框架。它不是LLM不会找到seed，也不是必须放宽协议。

改为仅应用idea显式轴，默认值只参与完整schema验证；同步和长期候选统一合并语义，拒绝消息保留具体漂移字段。来源支持的steps输入也同时进入可选候选列表，不再出现“API允许、选项菜单却排除”的双重合同。真实run只读复投影显示：旧seed 20261013→1000导致拒绝；新投影仅steps变化、冻结协议通过。不改baseline、原协议或bench源码。

数据arm记录还混淆了调用方的`{ref,quote}`与Supervisor的`{source_id}`引用契约。现在参数冲突、调用方来源错误、审查引用错误及科学前提不足分别封存证据／归属／下一动作。审查引用只允许一次有界格式修复，保留原科学判断和初始回复；未支持的判断不会因修格式变成通过。失败不作为“仓库不能采数据”的证据。

对完成train的attempt ID误调用inspect_native_job时，框架现在指出ID类别和read_evidence入口，不把“没有这个job目录”表述为原生作业损坏。Fix可按需只读candidate_jobs，仍不能热改协议校验器。

v13的Main自主提交b4产物的50集开发评测，job为`d344ac416b4a408aadf3d9e7dff68bfd`。原1200秒局部窗口不足以完成当前吞吐下的50集；01:54执行器在窗口中点给出资源复核事件，01:56 Main依据已完成rollout而非GPU利用率，自行申请5400秒，01:57执行器确认延期。原总预算和评测协议不变，操作者没有代为延期。02:19宿主仍确认同一worker在运行，到第35/50集；完整结果与正式候选采用仍待回收。该探针不能自动冒充正式测量：当前正式恢复路径需要原候选源码／策略／协议核验，不能为省一次评测便放松身份等价。

隔离故障注入发现，prelaunch恢复已经具备父回执、阶段、补丁清单、原生未启动和进程所有权检查，却还按`SourceCitationError`名称筛选准备故障。这样“同一安全恢复边界里的新异常类型”又会被遗漏。隔离修改以实际所有权证明决定是否可交回控制器，未写源码的准备故障回到paused；已有补丁则保留transaction、进入显式interrupted／discard精确回退，绝不自动重放未知作业。实际CPU候选的清单准备、写后提交、快照及消费者故障均可复验；不是新增benchmark错误码表，也不是宣称真实故障已经自治恢复。此修改尚未部署活跃v13。

另一个可复核缺口在可视化出口：17:40 Recorder两次把64位event_revision写成65位（第26字符起偏移），即使正文可读，仍因身份不匹配拒绝发布。事实表图保持更新，但新叙述和demo请求无法由这次失败写作进入发布链。隔离方案将模型输入的该字段改成绑定完整snapshot／event的短请求handle；执行器仍存原完整hash，并检查精确handle、引用、指标声明和独立事实审核。过期／错误handle仍拒绝，不通过给模型错误报告补上当前hash来追认。软件回归139项通过，真实发布与demo仍待验收。

原恢复模块和Recorder不在框架只读目录中，亦妨碍Main/Fix检查这些原因；隔离补入只读入口，不授予热改安全／报告核心的权限。该目录修正及新恢复／写作反例联合63项通过。上述发现说明应减少“实际状态一致、接口合同却分叉”的连接，而不是为了框架形式再增加职责或强迫所有仓库使用同一路线。安全窗口部署、真实复验、成本与实验出口须分别记录。
