# AutoSimSOTA 连续失败根因调查

日期：2026-10-01。对象：当前实现及 `robosyn_installrecovery_20261001_v1` 的实际轨迹。

## 结论

确实存在系统性的架构问题。不是简单的“RoboSyn 太难”“LLM 不会修复”或“预算不足”。当前框架在 Agent 判断与真实执行之间叠加了多层不一致的状态、权限、审批和命令队列约束；与此同时，持久化开销与流式输出背压正在使 Agent 运行器自身失败。

此前修复以局部异常为单位，缺少贯穿真实任务的验收。新增防护解决了一部分问题，也引入了新的回归。单元测试通过不等于系统完成一次真实采集、训练和评测；服务存活也不等于实验有进展。这是此前判断和交付标准不足之处，应由实现与验证方式承担责任，不能归咎于模型。

本次只调查并记录，没有修改生产代码、安装依赖、调用付费模型或重新启动实验。服务确认：`MainPID=0`、`ActiveState=inactive`、`SubState=dead`。保留现有环境、资源、轨迹与预算。

## 1. 调查依据与边界

核查了运行状态、原生执行回执、失败输出封存、修复审批事务和对应实现。另做了两项只读测量：真实日志的读取与哈希链校验，以及只读 Fix 的实际工具能力。

下文区分：

- 已证实：代码行为与实际回执相互印证，或已直接测量。
- 合理推断：有机制与数据支持，但尚未做修改前后的对照实验。
- 尚未证明：修复后能否完成真实闭环、能否提升指标，以及是否还有后续仿真兼容性问题。

本次调查不能证明所有历史失败都由同一个原因造成，也不能把当前环境准备失败解释为所有仓库缺少资源。

## 2. 已证实的关键问题

### 2.1 持久化日志进入执行热路径，且每条事件全量读写

文件：`autosim/autosim/research/research_state.py`，`_read_events` 第 84 行、`record` 第 206 行起。`agent_runtime.py` 第 1339 行起的 `emit` 同步调用该接口。

实际数据：

| 项目 | 实测结果 |
| --- | --- |
| `run_events.json` 大小 | 311,682,398 字节，约 312 MB |
| 事件数量 | 6,416 |
| 单次完整读取与哈希链校验 | 2.829 秒 |
| 测量进程峰值 RSS | 1,530,404 KiB，约 1.46 GiB |
| `run_state.json` 大小 | 1,666,618 字节 |

`record` 的所谓追加，实际是读取全部事件、校验全部哈希、追加一条、将整个 JSON 文件重新序列化并原子写回，再写状态快照。上述 2.829 秒只包含读取与校验，不包含重写、快照及文档刷新。

事件还保存阶段状态补丁，部分补丁重复携带累积历史，使日志增长快于仅保存精简事实的日志。逐事件重写整个历史会造成累计写入放大；“可靠记录”因此反过来阻塞运行器。确切端到端吞吐损失需要修复后对照测量，但这个热路径问题已经由源码和真实文件规模证实。

### 2.2 最近引入的事件队列把遥测与关键消息混在一起

文件：`process_executor.py` 第 375–384 行。异步读取将所有输出行放入容量为 8,192 的队列，溢出即报错并终止子进程。非权威的 `thinking_tokens` 进度消息也进入该队列，虽然之后投影阶段会忽略它们。

三份真实封存输出：

| 失败证据 ID | 输出行数 | `thinking_tokens` 行数 | 占比 | 退出码 / 超时 |
| --- | ---: | ---: | ---: | --- |
| `4c2d4a90e97d4f049a60918f4051dab8` | 8,448 | 8,399 | 99.42% | 143 / 否 |
| `4c549f81c2134554821d81a668dfbfc9` | 20,080 | 20,041 | 99.81% | 143 / 否 |
| `2d587093cfaf4d648047532b472fd585` | 18,169 | 18,130 | 99.79% | 143 / 否 |

来源：运行目录的 `agent/stream_failures/<ID>.json` 及同名 `.log`。`.log` 是封存对象，需先解析外层 JSON，再统计其 `stdout`；不是直接按文件物理行统计。

这是此前修改引入的回归。全量日志同步开销减慢消费者，无用遥测持续进入队列，溢出后框架主动杀掉 Agent。只扩大队列会推迟失败，不能修复机制。

注意：封存 stdout 已脱敏，部分数值字段被替换后不再是可解析的原始 JSON。不能根据这些脱敏行断言原始 CLI 输出损坏。这里统计的是仍可识别的消息类型，不将脱敏结果作为原始协议解析证据。退出码 143 单独也不能证明死因，需要结合队列故障轨迹。

### 2.3 Fix 的提示词与实际工具权限矛盾

文件：`agent_roles.py` 第 32–40、60、110 行起；`prepare.py` 第 4429–4474 行。

只读检查模式设置 `read_only=True`，同时关闭代码编辑与诊断执行。工具表只为 Scheduler 保留原生只读环境检查，未为只读 Fix 保留；但通用提示词仍要求使用 `inspect_native_environment`。

直接复现结果：

```text
readonly_fix_requires_native_inspection: True
readonly_fix_has_native_inspection: False
```

真实回执 `action_receipts/b78d948aa6b0a5c3.json` 中，Fix 明确报告所需工具未暴露，只能使用源码读取和历史证据。Agent 发现问题并不意味着有能力执行必要检查。

这是能力合同问题。修复应把“不能改源码”与“可以在真实解释器中做受限只读 CPU 检查”分开，而非给 Fix 任意 shell、网络或 GPU 权限。

### 2.4 审批提示词接受错误证据，校验器却只接受源码引用

文件：`provision.py` 第 1991 行起，尤其第 2090–2112 行。

审批器让模型依据源码和错误证据判断替换是否合法，但可信校验只允许 `file` 存在于本次源码片段映射，且引用必须精确包含在该片段中。运行日志、封存故障及请求字段没有独立证据命名空间。

实际事务 `review_transactions/75f47e39d9b61eab46fde499616f462f139ba2345473ae86704189e72b2ec4c6.json`：模型给出 `approved=true`，提出将 `--no-binary :all:` 收窄为仅针对 `toppra`，保留固定版本及源包哈希。四条引用包括三条源码和一条真实失败日志 `provision_attempts/a8633a4e6ea84684a72e780a1696ff43.log`。日志不是源码映射键，因此可信层将批准降为拒绝。

另一事务 `8d60fb61a527fd5a43348e9ddd8b25a70950d63f8887d1034bab6f1b177674ca` 带有超出六条上限的引用，提前被拒绝。引用越界需要约束，但不应丢失具体违规位置和可修正反馈。

更糟的是：部分引用不合法时，返回值仍保留模型的原始理由，清空引用，却没有说明哪条引用失配。于是 Agent 看到的可能是“拒绝 + 赞同修复的理由”。缓存事务标记 `completed` 也只表示模型响应完成，不表示可信审批通过。

应区分模型意见、可信批准和原生验证这三个状态。不能直接信任 `approved=true`；也不能以仅支持源码的校验器否定真实运行证据。

### 2.5 将旧安装命令错误地升级为不可改变的实验要求

文件：`provision.py` 第 1400 行附近的队列重建及后续 prerequisite 分支；`recovery_contract.py` 第 86 行附近的原操作复验边界。

“修复前置条件后重放原操作”对正确的操作有价值，例如缺少资源后重新运行原生评测。但当前环境队列也沿用这一约束：未经替换审批，原安装模板始终保留。模型试探得到的安装手段因此成为必须完成的义务，即使它不是用户目标的一部分。

实际轨迹中，安装构建工具和 `patchelf` 成功后，再次执行 `pip download --no-deps --no-binary :all: ... toppra==0.6.3`，耗时 812.1 秒失败，仍然是隔离构建依赖中的 `patchelf` 失败。成功安装目标环境中的构建工具，不能直接证明 pip 的临时隔离构建环境已经修复。[pip 官方构建说明](https://pip.pypa.io/en/stable/reference/build-system/)明确区分构建环境与运行环境。

证据：`provision_attempts/a8633a4e6ea84684a72e780a1696ff43.json`。此前一次 `patchelf` 安装成功耗时 482.5 秒，随后失败说明“安装命令成功”与“下游操作恢复”是不同后置条件。

应该冻结科学协议和目标能力，而不是冻结某条偶然生成的安装命令。允许证据支持的获取或安装路线改变，但仍要求固定版本/产物身份及真实下游消费者验证，不能用 import 成功冒充 rollout 成功。

### 2.6 Agent 子任务状态覆盖整个研究运行状态

文件：`research_state.py` 第 245–252 行；`agent_runtime.py` 第 1651 行。

每次任意阶段记录都会更新顶层 `phase/status`。某次 Agent 调用结束记录 `agent_finished/completed`，便会把整个 run 显示为 `completed`，即使 preparation 仍在 `running`。

本次只读测量直接读取到：

```text
latest_phase agent_runtime
status completed
preparation_status running
```

这不是实验成功，而是生命周期所有权混乱。它会误导 RUN.md、监控和恢复判断。只有研究编排层能决定 run 的完成；模型调用、原生作业、恢复事务各自有独立子状态。

## 3. 因果链：为何 Agent 没能自主修好

目前可还原的链条是：

1. 环境计划生成了有问题的获取命令，真实执行封存了失败。
2. Fix 能读取部分证据，但只读模式缺失提示词要求的原生检查工具。
3. 模型提出合理的路线修正，审批回应引用了真实失败日志。
4. 引用校验器只认源码，或因引用数量拒绝；反馈未清楚指向具体合同错误。
5. 队列保留原安装义务，继续补前置工具或重复同类操作，而未可靠更新目标能力的实现路径。
6. 各层持续产生状态和历史补丁；日志全量读写越来越慢。
7. 大量模型进度遥测塞满事件队列，Agent 被运行器终止，再进入框架恢复。
8. 子调用完成状态可能覆盖顶层状态，人类难以区分“模型完成了发言”和“实验推进了”。

链条中有实在的环境错误，也有错误诊断或不合格建议；不是所有 Agent 提议都合理。例如替换为不相关依赖、吞掉命令失败、只做 import 而跳过实际消费者，都应继续拒绝。需要修复的是一致的能力与证据合同，不是取消审核。

## 4. 与 AutoSOTA 的关键范围差异

本地 `AutoSOTA/cli_guide.md` 第 3、58、79、109 行明确要求：本地已克隆仓库，以及依赖/评测已可运行的环境。它的优化主循环建立在可执行评测入口上。

AutoSimSOTA 额外承担任意仓库资源发现、绑定原有环境、跨版本兼容、无人值守原生采集和仿真渲染等启动工作。这扩大了目标，但当前实现没有先把“保留并验证已有运行条件”做好，反而让研究入口长期困在环境修复。

因此，应优先支持资源与原生评测可验证的仿真仓库，先得到真实基线，再做数据优先优化。未知环境仍可尝试准备，但应作为独立的、能明确输出能力缺口的接入阶段。不能拿已配置环境的 AutoSOTA CLI 行为证明任意仿真仓库自动启动天然成立。现有本地材料也不足以逐行对照其最新完整实现。

## 5. 为什么此前修了这么久仍未解决

- 修复针对抛出的异常，而没有把目标能力、角色工具、证据引用、审批、执行和后置条件设计为同一份合同。
- 测试大量使用模拟审批结果和执行回执，能证明字段、红线和队列规则，却未验证真实模型响应、真实日志引用以及真实 pip 隔离构建共同工作。
- 以全套单元测试通过、服务存活作为较强完成信号，没有坚持真实消费者进展验收。
- 没有先测日志规模、消费者处理延迟和实际流式消息构成，就加入可靠事件队列，导致新的背压回归。
- 反复续跑使历史和旧队列不断累积，未消除原有错误义务，修复与恢复的成本越来越高。

此前新增模块不是全部无用：证据封存、隔离工作区、总预算、原生回执和科学红线都应保留。但必须减少重复权威层，让它们围绕真实能力验证工作，而不是继续增加失败特判。

## 6. 推荐整改顺序与验收

这些是调查后的方案，尚未实施，不能标记为已解决。

| 顺序 | 改动 | 必须验证的结果 |
| --- | --- | --- |
| P0-1 | 日志改为追加式事件记录，增量验证；大证据和累积历史通过稳定 ID 引用；快照与 RUN.md 脱离逐消息热路径 | 在当前历史规模下追加不会重写整份历史；中断后能验证和恢复；吞吐与内存有实测 |
| P0-2 | 区分关键结果/工具回执/错误与非权威进度遥测，在进入可靠队列前合并遥测 | 重放真实三份输出，无关键消息丢失、无队列溢出；另测慢消费者和断流 |
| P0-3 | 分离 run、Agent 调用、原生作业、恢复事务的状态所有权 | Agent 完成不能结束 run；RUN.md 正确显示仍待验证的能力及当前阻塞 |
| P0-4 | 建立角色能力清单并在调用前验证提示词与工具一致性 | 只读 Fix 可做受限真实环境检查，不能修改源库、访问任意资源或占用 GPU |
| P0-5 | 统一带类型的证据引用：源码片段、原生故障、资源、拟议操作；返回逐项校验错误 | 真实失败日志可作依据；伪造引用仍拒绝；缓存区分模型意见和可信批准 |
| P1-1 | 环境按缺失能力推进，安装命令只是可替换实现；替换明确声明保留的后置条件 | 合法换路线后旧模板退役；禁止跳过科学评测；下游消费者实测恢复 |
| P1-2 | 先探测并连接现有解释器、配置、资源和消费者，再决定是否重建 | 已可用环境不被无条件重装；资源存在不等于可被当前任务消费 |
| P1-3 | 无进展按能力缺口升级，而不是重复同一命令；每次恢复必须产生新的可检验依据 | 同类失败无新增证据时不无限重试；给出剩余问题与可执行下一步 |
| P2 | 固定一个真实闭环验收，再验证跨仓库 | 自主采集少量合法数据 → 真实训练产物 → 实际加载 → rollout → 指标；不以准备阶段结束替代 |

### 真实闭环验收的底线

1. 全程由系统选择并执行，外部人工不替它修改安装命令、训练配置或数据目录。
2. 保存每个阶段的原生回执、数据与 checkpoint 身份、实际消费者加载证据。
3. 注入一项可恢复故障，系统自主修复，并通过同等能力的原生后置条件；不能仅报告修复成功。
4. 断点恢复不重复已证实可用的资源获取，不把旧命令当作不可撤销义务。
5. RUN.md 用中文说明阶段、结果、失败依据和下一步；真实指标比较与可用 demo 来自真实产物，不虚构。
6. 小闭环通过后再跑正式基线及候选计分。随后在另一个资源可复现仓库测试，不能只用 RoboSyn 特判证明通用。

## 7. 未决事项与停止重跑的条件

当前 checkout 的任务包与 EmbodiChain 版本仍有兼容性缺口，不能声称所有资源问题已解决。日志中曾发现现有版本不提供所需任务包；另一资源版本的发现不等于已安装并被真实任务使用。

此外，正式训练、仿真渲染、checkpoint 加载、评测身份以及指标改善尚未被本次停在准备阶段的轨迹验证。解决上述架构问题之后仍可能暴露下游故障。

在 P0 的真实输出重放、证据审批和状态验收通过之前，不应再次启动长期研究运行。下一轮应是限定范围的工程验收，而不是又一次依赖长时间运行碰运气。保持当前 run 停止；本报告不作修复已完成或可以 AutoSOTA 的承诺。

## 8. 按用户后续授权实施的修复

以下是调查之后的实现记录，不覆盖上文调查时的事实。

1. `ResearchStateStore` 在历史达到 128 条或 1 MiB 时迁移为 schema 2 清单、不可变 `run_events.legacy.json` 和 `run_events.jsonl`。迁移保留旧字节与事件哈希，不重新复制或篡改事件。冷启动通过流式 SHA-256 验证旧历史；当前写入器使用已核验游标，外部日志变化则重新核验。跨写入器仍通过原文件锁串行提交。日志追加与快照写入分别持久化，快照失败可回放。
2. 超过 64 KiB 的阶段补丁、超过 16 KiB 的事件详情使用内容摘要引用，不重复放入事件流；补丁回放读取并校验内容摘要。快照保留完整当前状态，兼容旧读者。损坏或不完整事件仍拒绝采用，不以猜测修复权威证据。
3. Agent 的已知思考遥测在进入关键队列前过滤；原始输出仍完整捕获并受总量上限约束。保留未知记录、工具消息、错误和最终结果；不修改调用的模型预算或权限边界。
4. 生命周期由 preparation/research 控制，Agent 等子任务只更新自己的状态。恢复代码显式读取子任务的进程身份，旧快照的顶层 Agent 状态可规范化为真实父阶段。RUN 的 schema 2 展示仅核验和读取有界尾部，明确标记投影范围。
5. 只读 Fix/Init 可使用受限原生环境检查，MCP 同时带只读与原生检查标志，不开放任意命令或源码编辑。其他无检查能力角色的提示词不再要求调用该工具。
6. 审批有源码、原生失败/成功、拟议操作命名空间，运行证据通过稳定 ID 和日志哈希读取。允许旧格式日志引用映射到已验证证据；未知路径或伪造引用不能成为依据。引用错误反馈指出具体位置；模型批准与可信校验分别记录，RUN 用中文显示拒绝及待修正项。
7. 安装替换审核允许对不适合或过度限制的获取路线改用等价实现，仍保留包/产物身份及消费者能力。非队列批量退役的替换也传递全部原有探针，避免审核遗漏下游要求。旧队头只在可信批准后退役，不直接相信模型的 approved。

### 实测与证明范围

## 9. 2026-10-02：第二轮环境恢复修复

进一步审计发现：控制层仅凭解释器可能把失败构建报为 done；失败探针没有像安装队头一样持久化“先修再验”义务；合作式 checkpoint 提前返回，使旧的无进展 reconsider 不足以阻止空转；无本地 wheel/候选的资源清单会自动批准不可构建。这些是通用框架缺口，不是 RoboSyn 名称的特殊问题。

实现分别补齐 verdict 门控、`native_probe` 失败域、失败探针游标与旧游标兼容、未接受修复不重放、Fix 意图调用前持久化去重，以及全部资源边界的说明/独立审核。意图包含失败、执行输入、源码内容、所选环境元数据和资源清单；仅改 reasoning 不解锁，真实变更或明确修正提案可再试。源码扫描有界，失败不能被当作不存在或导致恢复直接崩溃。仍不通过硬编码 benchmark、自动删除队列或放宽科学协议解决问题。

新增只读、无网络、无 GPU 的所选解释器元数据观察：收集 distribution/version/import-name hints，封存日志；按上下文、元数据和实现身份缓存，复用前校验证据哈希。Fix 获得相关条目和完整证据 ID，Scheduler 获得缓存摘要；没有展示的条目不代表没有安装，元数据也不证明 import/任务/API 可用。真实 task loader、模块命名空间和版本兼容仍交给 Agent 按源码与 native_probe 判断。探针替换审核可引用独立封存成功证据，不以安装队列退役为前提。

真实停止 run 的只读事实仍包括：`toppra 0.6.3` 已有安装和导入证据，但队列保留源码获取路线；已安装 distribution `dexsim-engine` 的导入名提示是 `dexsim`，不是旧探针要求的 `dexsim_engine`；所选环境中缺少部分任务/训练依赖，实际任务引用的 `embodichain_tasks` 与检出的 EmbodiChain 任务命名空间不一致。这些事实说明 Agent 应复核已用资源及消费者版本，不能只重复 pip，也不能靠 metadata 把消费者标为通过。本轮没有手工补包、改任务导入或改真实游标，因此不声称真实环境缺口已经消失。

新增回归覆盖通过/失败 verdict、协作和非协作失败探针、旧游标、同证据 Fix 去重、源码与环境变更解锁、空本地资源边界、相关目录的非缺失语义、缓存篡改与失效，以及 `/tmp` 临时 Python venv 的真实只读元数据执行/封存。模型回复使用测试替身，不是 LLM 自主恢复或仿真验收。全量结果见执行进度；服务再次只读确认 MainPID=0、inactive/dead。
