# AutoSOTA 与当前系统:框架流程的逐项对比

AutoSOTA([arXiv:2604.05550](https://ar5iv.labs.arxiv.org/html/2604.05550),[代码](https://github.com/tsinghua-fib-lab/AutoSOTA))是清华 FIB 的端到端自动研究系统,105 篇论文、每篇约 5 小时、平均 +10%。这份文档把它的控制流和当前系统逐项对齐,并分清**哪些差异是有意的**、**哪些是真实的缺口**。

---

## 一、两条流程并排

| | AutoSOTA | 当前系统 |
|---|---|---|
| **输入** | 一篇顶会论文(PDF)+ 它的官方仓库 | 一个 benchmark 仓库 |
| **目标是** | 超过论文报出的那个数 | 找到比自测基线更好的配置 |
| **准备** | AgentResource(仓库定位 + 外部资源注册表 + 获取)→ AgentObjective(BFS 评分表)→ AgentInit(环境、仓库修补、命令发现) | survey → scout(声明)→ provision(环境)→ derive(阶段 + 命令) |
| **循环** | Phase 0 基线 → Phase 1 探索仓库写 `code_analysis.md` → Phase 2 建 Idea Library + 红线审计 → Phase 3 逐轮七步 → Phase 4 恢复 `_best` | baseline measure → 建评分表 → 建想法库 + 红线审计 → 逐轮：选想法 → 快照 → 改 → 测 → 有用则留、无用则回滚 → compare |
| **支撑** | AgentMonitor(循环外)、AgentFix(三层失败记忆) | `awareness`、`monitor`、`failure_memory`(已对齐) |
| **产出** | `_best` 标签、docker 镜像、导出的仓库 | `measurements/*.json`、`RUN.md`/`RUN.html`、`runs.json` |

---

## 二、有意的差异(不该对齐)

**1. 输入不是论文。** AutoSOTA 的起点是一个**主张**(论文报的数)。因此它知道目标在哪、知道该复现什么、Phase 1 有"读懂这篇论文的方法"这件事可做。我们的起点是一个 benchmark,**没有目标数,只有自己测出来的基线**。这不是缺陷,是两个不同的问题:他们改进已知的方法,我们在一个环境里做实验。

**2. 所以"复现论文"这一步在我们这里不存在。** 他们 root 节点的定义就是"完整复现论文";我们没有对应的东西,也不该有。

**3. 不做容器编排。** 他们有 docker、镜像层提交、2 卡为一个调度单元。这套系统一贯的纪律是"产物就是记录",`job_runner`/`leases` 走的是另一条路。

---

## 三、真实的缺口(值得看)

按我认为的重要性排。

### 缺口 1:提案没有类型,因此搜索空间只有一类

AutoSOTA 给每个想法打粒度 `τ(h) ∈ {PARAM, CODE, ALGO}`,并明确报告 51% 的改进来自算法创新、33% 来自调参。**它的搜索空间是"这份仓库的全部源码"**——论文里专门说这是对 AutoML 封闭搜索空间和 AlphaEvolve 沙箱的超越。

当前系统的 `propose` **只能从声明好的优化空间里命名设置**。用他们的词说,我们只做 PARAM。`derived_research` 里那条把 `proposal["training"]` 展平成 `f"{key}.{k}"` 的代码就是这个限制的形状 —— 它只会拼 `name=value`。

这是最深的差异,而且不是"缺一个功能":**声明空间本身是从仓库读出来的轴,轴之外的东西系统看不见。** 要动代码,需要有"改哪个文件的哪一段"这条通道,以及验证它没改变评测的红线。

### 缺口 2:没有 Idea Library —— 每轮从零再想一次

AutoSOTA 在 Phase 2 **一次性**建一个 ≥10 条的想法库,每条带类型、风险、粒度,然后 Phase 3 每轮只是**选择**;只有当连续三轮都是 PARAM 时才被迫走 Leap Path 重新合成。

当前系统**每轮现场生成一个提案**。所以:

- 上一轮想过但没选的方案,下一轮不会被记住(只有试过的记在 failure memory 里)
- 没有"想法之间互相比较"的场合
- 控制器每轮都在从证据重新推导,而不是在一个已经想清楚的集合上做选择

### 缺口 3:反停滞是刹车,不是换挡

AutoSOTA:连续三次 PARAM 就**强制走 Leap Path**——一条结构上不同的新想法,并给它一个**蜜月期**(最多 5 轮探索/调试,不行再回滚到 Leap 前的最优点)。

当前系统:我加的 `obstacles_in_a_row >= 3` **停止**这个阶段。

区别不是程度,是方向:他们**换一类动作继续**,我们**停车**。今天 RoboTwin 上三个阶段都是在"三次之后停车"结束的,而正确的下一步是换一类动作(比如从改命令行换成改仓库)。

### 缺口 4:没有 `_best`,也没有回滚

AutoSOTA:每次修改前 git 快照(七步里的第 2 步),`_best` 标签由 `record_score.sh` 原子前移,崩溃或调试预算耗尽就 `git checkout` 恢复,Phase 4 恢复 `_best` 并重测。

当前系统:
- `repository_autoresearch` 有 `_select()`,保留最优候选 —— 但**派生循环没有**
- `derived_research` 的失败只会让这一轮没有数字,不回滚任何状态
- 没有"最好的一次"这个标签

对派生路径,这意味着**一个把环境改坏的尝试会留在那里**,后面的轮次都在坏状态上跑。staging 尤其如此:它写的符号链接一旦错了,下一次运行仍在。

### 缺口 5:目标是一个数,不是一张评分表

AutoSOTA 把宏观目标做 BFS 分解成二叉 Pass/Fail 子任务,权重守恒地往下分,到阈值或最大深度停止;浅层注入摘要、深层注入代码细节。

当前系统 `measure()` 的产出是 `success_rate` 加一组 `readings`。`readings` 里其实有更多数字(loss、动作步数、推理耗时),但**决策只按 success_rate 排序**,没有"哪些子目标达成了"这一层。

方法库里已经有 `progress-beats-binary` 和 `resolution-before-repetition` 两条相关技能 —— **知识在,harness 没接**。

### 缺口 6:红线是使用点检查,不是事前审计

AutoSOTA 的 Red Line System 是七条写死的禁令(R1 指标参数固定、R2 评测脚本不动、R3 预测必须来自真实推理、R4 不许跨指标取舍、R5 划分不变、R6 不许改数据分布、R7 逐论文约束),而且**每条想法在跑之前就被标 REJECTED / CLEARED**,审计表在 `idea_library.md` 里。

当前系统的对应物是 `assert_frozen`(评测时冻结文件比对)和 `values_the_program_contradicts`(声明与程序矛盾),都是**在用到的那一刻检查**。这有它的好处(不依赖事前判断),但少了一样东西:**一个提案在被执行前没有经过一道"这条是否越过红线"的关卡**,越界的结果是运行到一半失败,而不是被拒绝。

## 四、已经对齐的

- **三层失败记忆** —— 签名归一化、跨仓库检索、蒸馏成技能。对齐。
- **检索在推理之前** —— `what_this_failure_has_looked_like_before` 进 payload。对齐。
- **循环外的观察者,给高层指引而不给修法** —— `monitor`。对齐。
- **按需取用而非灌入** —— 他们的"on-demand command-line retrieval",我们的 inspection loop。对齐。
- **协议保持的仓库修补** —— `staging` 是他们的 "protocol-preserving repository repair" 的最小可检查形式。对齐。
- **产物即完成证明** —— 他们按 artifact 存在/内容验证完成,我们 `check_artifact`。对齐。

## 五、如果只做一件事

**缺口 3(换挡而不是刹车)**,因为它是今天唯一一个系统**已经诊断对、却停下来**的地方。三个阶段的停止理由都是准确的发现,而循环对准确发现的回应是结束。

实现上和缺口 2 是同一件事的一半:需要有一个"想法的空间"可供换挡 —— **不一定要先建十条,但至少要有"这一类已经试够了,换一类"这条通道**,而且换的那一类要能被表达(这就是缺口 1:目前能表达的只有 PARAM)。

**缺口 1 和 2 是同一个根**:提案的形状决定了搜索的形状。当前提案的形状是"从声明空间里取值",因此循环的搜索形状也只能是"在这个空间里换值"。AutoSOTA 的提案形状是"一个带类型、带粒度、带红线的改动",因此它能换的不只是值。

## 六、补齐之后

六个缺口都动了,每一条都落在一个模块上,不是加在循环体的分支里。

| 缺口 | 落在哪 | 一句话 |
|---|---|---|
| 1 粒度 | `ideas.py` | `Idea.granularity ∈ {param, code, algo}`,`code` 的 `change` 是 `{file, find, replace}` |
| 2 想法库 | `ideas.py` + `derived_research.choose_idea` | 一轮建库、每轮只选;选是规则不是模型调用 |
| 3 换挡 | `ideas.needs_a_leap` + `ideas.leap` | 连续三同类 → 造一条不同类型的,而不是停车 |
| 4 快照 | `snapshot.py` + `codepatch.py` | 改前拍、无效精确回滚、`_best` 只在更好时前移 |
| 5 评分表 | `objective.py` | 主干 + 该 benchmark 自己的子问题,权重守恒,报完成度 |
| 6 红线 | `redlines.py` | 整批在跑之前审计,越界的在库里标 rejected |

### 实现时被改掉的三个判断

写下来是因为它们都是同一种缺陷:**一个对坏状态也通过的检查**,或者**一个把被它保护的东西弄坏的守卫**。

**一、`_best` 不能只有一把尺子。** 完成度 0.6 不是比成功率 0.4 更好 —— 它们是两个问题。第一版把它们放进同一个 `advance()` 比较,于是"更靠近能测出数字"会挤掉"已经测出了数字"。现在 `score` 带 `scale`,两种刻度互不比较,已测出的那个永远优先。

**二、"未到达"不等于"没通过",但也不等于什么都没发生。** 第一版让 `passed is None` 的节点一个子节点的分都不拿。RoboTwin 正是这个情形:评测从没产出数字,而"求值器被指向了 benchmark 自己的初始状态"这个子问题是被真观察到的。同一类错误会在两个地方出现——`score()` 和 `frontier()`——因为它们读的是同一个 `None`。

**三、审计的判定词和想法的状态词必须是同一个词。** `redlines.CLEARED = "CLEARED"` 与 `ideas.CLEARED = "cleared"` 让 `idea.status != redlines.CLEARED` 恒为真:一条**通过了**审计的跃迁想法被当成被否决,而没有任何地方报错。已统一为小写,并加了一条断言两者相等的测试。

### 一处刻意的不同

`_best` 不是 git 标签。AutoSOTA 往论文仓库里写 commit 来记快照;这里写的是按内容寻址的 blob,放在运行自己的目录里。理由和这个系统别处一样:为了记一次实验而对用户仓库的历史动手,比这次实验本身的副作用更大。快照覆盖的是**这次运行自己动过的文件**,不是整份 checkout。

## 七、RoboTwin 复测说明了什么

跑了很多遍,每一遍都暴露出真缺陷。最后一遍的形状:

| 轮次 | 想法 | 类型 | 结果 |
|---|---|---|---|
| 0 | baseline | — | evaluate 没跑出命令,没有数字 |
| 1 | `action-dim-from-hdf5-not-code` | code | 修补后模型放弃:「这个文件里没有这条想法要找的那行,意图无法按现状实现」 |
| 2 | `decouple-eval-gym-prefix` | code | 修补成功 → 应用 → 跑 → 没出数字 → **回滚** |
| 3 | `episodes-from-seeded-stream` | algo | 请求 collect,而该 benchmark 没有采集器 → 记为提议失败,不结束运行 |
| 4 | `normalize-ckpt-dir-layout` | code | 修补成功(`bench_name` 在文件里出现两次,改成锚定两行)→ 跑 → 没出数字 → **回滚** |
| 5 | `train-then-eval-chain` | algo | 应用、跑、没出数字;**没有文件可回滚** |
| 6 | `collection-randomization-...` | algo | 同第 3 轮 |
| 7 | — | — | 库里剩下的都是 param,而没数字时只有 code/algo 可能有用 |

**做到的事**:循环八轮全部走完,没有一次因为"诊断正确"而结束;两次代码改动被精确回滚;两次修补拒绝得诚实(模型自己说这条改不了);评分表给出了 RoboTwin 自己的 11 个子问题,完成度 0.4;`_best` 停在 progress 刻度上。

**没做到的事**:RoboTwin 的评测**仍然没有跑起来**。原因是上一层的推导没为 `evaluate` 找到命令(`--keep-only` 跳过重推),而循环的想法还没有一条能让它跑通。所以关于**框架**的问题有了答案,关于**这个 benchmark** 的问题还没有。

### 复测中发现并修掉的缺陷

每一条都是同一类:一个对坏状态也通过的检查,或一条到不了目的地的判断。

1. **`algo` 被送进了 `code_change`** —— 七轮里四轮死在"给我一个 `find`",而 `algo` 从来不携带文件。两种改动形状不同,走的路也必须不同。
2. **想法库的 `param`/`algo` 想法过不了 `validate_proposal`** —— 因为库里没有 `decision`/`proposal_id`/`expected_validation`。信封是协议的,由循环补;空间要检查的是改动本身。补的时候顺手把"未指定的必填轴"填成声明的默认值。
3. **`check_space` 与 `validate_proposal` 对同一个属性给出不同规则** —— 前者用 `accepts(None)` 判断"必填但填不出值",后者无条件要求。于是 `task_selection.task_name`(structure 轴、无校验器、接受 null)被一处说可以不填、另一处要求必须填,每条不巧没写它的想法都被拒。两处已统一。
4. **放弃"没有基线就别想了"的同时,漏掉了它的孪生兄弟** —— 请求了 benchmark 没有的数据时,循环仍然直接结束。修法是区分来源:声明空间会给出同样的答复,所以停;想法库里还有别的想法,所以继续。
5. **默认值被当成了请求** —— 信封为了通过校验,替每条想法把整个 `collection` section 填满默认值;循环便以为作者要求采集,于是八轮里四轮花在请求一个不存在的采集器上。请求应当来自作者。

### 一个走过又退回来的弯路

上面第 6 条原本是:**模型把 section 套进 section、把轴拆在阶段名下面 —— 写一个 `_hoist` 把无歧义的嵌套读回来**。它被实现了,先是处理 section 套 section,然后又加了阶段名,然后又加了 `train.n_epochs` 的拆写。**三次修补,三种拼法。**

用户指出这仍然是堆砌规则:模型每出现一种写法就加一条规则去接,而规则只覆盖写它的人见过的那几种。同一轮里还有提示词在长——"RoboTwin 因此损失了三轮"、"RoboTwin 在那上面花了七轮中的四轮"——那是把观察到的失败编码成禁令。

**框架层本来就有更好的答案,而且是我自己写的**:`ideas.repair` —— 把拒绝的理由和模型缺的那个事实一起给它,让它自己改。它当时只用在补丁上(四次修补,三次改对,一次诚实放弃)。同一个通道打开到形状上之后:

- `_hoist` 整个删掉(55 行)
- 两条战例段落删掉
- 校验失败和补丁不合走**同一条**修补路径:给它文件的原文,给它这个 benchmark 真正声明的 sections 和 axes

RoboTwin 上,改之前八轮里三轮死在形状上;改之后八轮里六轮是真实工作,零轮死在形状上。放弃的那一轮,模型自己的话是:"声明的 sections(collection, training, task_selection)没有 `action_dim` 轴,所以这个维度改不了" —— 它在读给它的空间,然后从事实上推理,而不是在猜一种被接受的写法。

**规则覆盖作者见过的拼法;机制覆盖没人见过的。** 这是这个项目一贯的那条线,只是我又走回去了一次。
