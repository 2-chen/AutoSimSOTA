# 环境要能执行，而不仅是安装成功

方法性指引。检查当前 Python、依赖锁、原生扩展、驱动/GPU 架构、仿真/渲染与资源权限。过去某仓库可用的版本组合只可作线索，不是跨仓库默认值。

用最小真实操作验证：GPU 张量计算、环境 reset/step/读取一帧、模型 forward 或训练导入。is_available、包能 import、命令 exit 0 各只支持有限结论，不证明整条链路可用。

读取完整错误或稳定证据 ID，区分缺包、二进制 ABI/版本不兼容、缺设备/显示/资产、权限与资源不足。先检查官方兼容说明和本机证据，再决定 pin、升级或局部补丁。构建日志中的 workaround 也要核对适用范围与副作用。

显示/渲染错误要核验两条独立连接：仓库的 headless 配置是否实际到达 renderer，以及底层显示驱动/离屏实现需要什么环境。一个 headless 标志不证明 SDL/GL/Vulkan 等底层已配置；CUDA 成功也不证明能读相机帧。依据当前源码、官方说明和原错误选择最小无显示探针，不统一设置某种 driver、启动 X server 或改渲染器。不要关闭图像观测/录像、改成功条件来掩盖初始化错误。

资产正在下载与下载失败分开：核对原生日志、实际字节和已有授权缓存，完成后复用同一 run-owned 缓存。新隔离 HOME 不代表 SDK 资产已经连接；不要完整复制旧 HOME 或关闭隔离来复用缓存。已声明的 import/文件消费者通过后，仍可在命令验收中发现 reset/render 缺口；只恢复缺失能力，不重装全部环境。

只改 run-local 环境；重建环境可能丢失已有配置，应保存解析依赖与构建过程并重新验证相关路径。不要修改系统驱动、共享环境或源仓库来临时掩盖错误。安全隔离导致的问题应按权限边界处理，不以关闭隔离为通用修复。

每次修复说明假设、变更与原失败操作复验；重复同因错误先读历史，避免无新证据循环安装。保留版本、平台、执行证据和可迁移的步骤，不把机器绝对路径固化为通用技能。

授权继承研究可提供原生调用历史参考：它是已封存的连接经验，不是新环境/新仓库的批准。优先保留已解决的解释器、配置、资源及渲染连接，再适配当前输入并复验；不能直接复制旧数据根、权重、训练量或评测条件。需要GPU初始化的渲染构造在CPU诊断中因设备隐藏失败，不证明headless不存在或真实GPU不可用；读源码、请求受控GPU小试，不循环更换CPU中的渲染器。
