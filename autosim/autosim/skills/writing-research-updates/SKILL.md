# 写给研究者看的运行记录

读者想知道：系统正在解决什么、做了什么、发现了什么、这意味着什么，以及接下来会发生什么。用一段能独立读懂的说明回答这些问题，再给必要的证据入口。默认使用简体中文；用户指定其他语言时遵从用户。

## 写之前先核对

读取当前 ReportView、上一版叙述和本次新增证据；缺少 ReportView 时使用任务提供的原始回执，并说明信息截至何时。先区分：

- 进程/模型是否存活，最近是否有工具活动，实验是否获得了新证据，是否产生了有效测量。心跳更新只支持第一项。
- 外层 run、当前动作、候选和模型会话各自的状态。子循环 completed 不代表研究目标完成。
- 已核验事实、Agent 的诊断猜测、仍缺少的证据。较新回执可以推翻旧摘要，不能反过来。

先读最后一次实际失败的回执和日志摘要，再解释停止原因。若这些证据不可访问，说清楚缺的是哪条证据；不要把“我不能读日志”写成“仓库缺少资源”。

## 把轨迹组织成故事

开头直接说明当前结果和最重要的变化。随后围绕少量有因果关系的实验片段写作：原先要验证什么，采取了什么行动，出现什么观察，哪项认识因此改变。合并同一问题的重复尝试，交代次数口径、成本及是否得到新信息，不逐条翻译事件日志。

日常更新通常一到三段，终态复盘可以更长；按信息量决定篇幅。首页保留当前结论、关键进展、必要的结果表和媒体；完整命令、会话 ID、哈希、JSON 与调用流水放到可点击详情中。自然语言不必机械复述所有字段。

先说含义再给术语。例如把 `adaptation_unresolved` 解释为“运行已结束，系统尚未接通有效评测”；把 `unscored` 写成“未得到有效分数”。同一次文档统一使用配置的时区，区分最后活动时间、叙述依据时间和文档刷新时间。

## 让结论与证据相称

数值必须绑定对应样本、单位、比较对象和来源；只有数字在日志中出现不够。没有分数时写“未测得”，不能写成功率 0%。阶段耗时未知时写未知，不能显示 0 秒。模型费用的估算、已结算部分和未知用量预留分开说明；墙钟时间不能当作 GPU 小时。

回退、未评分候选、失败与人工介入都属于实验结果。没有可比较基线时，说明当前仍在接入/恢复阶段，不称为已完成优化或找到最佳策略。文件存在不证明它被本次评测加载，正常退出码不证明评测完成。

每个关键结论附简短证据链接；事实绑定和 `based_on_revision` 放报告元数据或详情，不让机器字段占据正文。新证据推翻旧结论时明确更正，例如“此前把缺少产物误写成缺少模型实现；源码已确认模型实现存在”。

已发生的事实与下一步建议使用不同语气。未执行的修复写成“下一步应……”，不要写成“系统正在……”。没有明确下一动作的终态，应直接说运行已停止。

## 交付前自查

读者只看首段，能否判断运行是否继续、有没有有效结果、当前阻碍是什么？删去只有内部角色名、动作名或 schema 字段而没有实际含义的句子。核对结论是否来自最新证据，有无把推测、部分任务结果或代表性视频写成完整结论。

若输入只有心跳且无新研究信息，建议保持原叙述，只刷新状态栏。若缺少证据或模型服务不可用，给出简短中文事实说明及缺失原因，保留上一份仍有依据的解释。

本 skill 只提供写作方法。它不授予代码、账本、评分或作业权限；叙述由运行器保存，权威事实由确定性发布器核验。需要展示仿真媒体时，按需读取 `presenting-simulation-demos`，而不是自行启动仿真。
